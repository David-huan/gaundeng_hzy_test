# 无效面试瓶颈分析与候选人筛选器

## 这个项目是做什么的

业务快速扩张后，面试官的时间被大量**无效面试**（爽约、未能形成有效评估）占用，用人部门推进效率受阻。本项目做两件事：

1. **找瓶颈**：用 `interviews.csv` 的 1181 场历史面试记录，分析哪些渠道、部门、评分、时段的组合最容易产生无效面试，定位真正的根因（结论：员工内推 × 研发/产品运营/客户成功 三个部门，无效率 50.2%）。
2. **筛人选**：由 `test.py` 按分析出的规则把候选人分成两档并导出 `screened.csv` —— 高风险分组**先人工复筛**再约面（12 工时成本），低风险分组**直接安排面试**，把面试官精力集中在最值得深入沟通的候选人身上，减少工时空耗。

简言之：**从历史数据里找出无效面试卡在哪，再用一条可执行的规则筛掉高风险候选人，帮面试官省时间。**

## 一、我的判断

### 看到了什么

全量 1181 场面试中，1137 场有结果判定（44 条 `is_valid` 为空，占 3.7%，已从无效率分母剔除），其中 **147 场无效，整体无效率 12.9%**。按业务口径（每次爽约损失 75 工时），这 147 场共吞掉 **11,025 工时**。

无效面试不是均匀分布的，它高度集中在一个**交叉点**上：

| 分组 | 判定数 | 无效数 | 无效率 |
|---|---:|---:|---:|
| **员工内推 × 非商业销售部**（研发/产品运营/客户成功） | **225** | **113** | **50.2%** |
| 其余全部（含商业销售部内推、全部其他 7 个渠道） | **912** | **34** | **3.7%** |

拆到部门维度看更清楚（员工内推，仅判定口径）：

| 内推 × 部门 | 判定数 | 无效数 | 无效率 |
|---|---:|---:|---:|
| 客户成功部 | 75 | 40 | 53.3% |
| 产品运营部 | 60 | 30 | 50.0% |
| 研发部 | 90 | 43 | 47.8% |
| 商业销售部 | 78 | 4 | **5.1%** |

其他 7 个渠道的无效率全部在 **1.7% ~ 6.0%** 区间，彼此差距很小；即使单看"员工内推"这一条渠道整体 38.6%，也远不能解释到 50.2% 这个量级——必须到 **渠道 × 部门** 这一层才看得见。

### 根问题是什么

**瓶颈不在候选人质量评分，在内推渠道的准入放行。**

三个证据把其他可能性都排除了：

1. **不是分数问题**。按 `match_score` 六档分层，复筛池内无效率是 52.2% / 52.9% / 47.1% / 48.9% / 52.6% / 46.2% —— **完全不随分数单调变化，最高分段(26-30)照样 46.2% 无效**。说明给内推候选人打分再高也筛不出风险，分数这个抓手在此分组内失效。
2. **不是时段/星期问题**。表面看 10 点(24.6%)、21 点(18.8%)无效率高，但按渠道拆开后：各时段非内推无效率稳定在 0%~8.5%，而内推各时段 18%~62% 都高。**时段差异是内推的混杂效应**，不是独立成因。
3. **不是简历阅读时长问题**。`resume_duration_min` 越长无效率越高（<30 分钟 4.5% → 75+ 分钟 22.6%），但在非内推内部各档只有 0%~5.6%，平的；长时长只是"内推候选人面试官看得更久"的影子。同理，**没有发现它与分数的交互作用**（低分档无效率最高仅 18.4%，远低于内推池的 50.2%）。

**根因表述**：研发部 / 产品运营部 / 客户成功部 三个部门通过员工内推通道进来的简历，在面试前缺少有效的人工复筛把关，约一半走到面试环节才被判定无效（爽约/无法有效评估），面试官时间被稳定消耗。商业销售部的内推无效率只有 5.1%（chi²=49.7，与其余三部门差异显著），说明内推通道本身并非必然失控，而是**这三个部门的内推准入流程缺失**。

## 二、做了什么

把 [test.py](file:///f:/programming/project/gaundeng/test.py) 从占位文件改写成**筛选适合的人的程序**，一条命令完成「诊断 → 分档 → 输出」：

- **诊断**：按渠道、部门、渠道×部门交叉、match_score 分层四个维度算无效率，并给出经济账。
- **分档**：给每条记录打 `screen_action`
  - `PRE_SCREEN`（需人工复筛）：`channel == 员工内推 且 department != 商业销售部`
  - `DIRECT`（直接安排面试）：其余全部
- **输出**：[screened.csv](file:///f:/programming/project/gaundeng/screened.csv)（1181 行，含原字段 + `screen_action` + `screen_reason`）

核心判定逻辑只有两行：

```python
def need_rescreen(row):
    return row.get("channel") == "员工内推" and row.get("department") != "商业销售部"
```

规则刻意做窄（排除商业销售部），而不是"全部内推都复筛"，因为这样用 **225 次复筛覆盖 113/147 = 76.9% 的无效面试**，而"全部内推"要用 303 次才能覆盖 79.6%——多花 34 次复筛只多覆盖 4 场。

## 三、怎么证明有用

### 口径（业务给定）

- 每次无效/爽约面试损失 **75 工时**
- 每次提前人工复筛花费 **12 工时**

### 直接测算

| 项目 | 数值 |
|---|---:|
| 全量无效面试 | 147 次 → **11,025 工时** 损失 |
| 复筛池规模 | 225 次（占全量 19.1%） → **2,700 工时** 成本 |
| 池内无效面试 | 113 次 → 上限收益 **8,475 工时** |
| 净收益上限 | 8,475 − 2,700 = **+5,775 工时** |
| **盈亏平衡拦截率** | 12 / (50.2% × 75) = **31.9%** |

即：**复筛这 225 人，只要拦下不到三分之一就回本**；池内实测无效率 50.2%，天然远超这条线。敏感性测算（脚本自动输出）：

| 实际拦截率 | 净工时 |
|---:|---:|
| 30% | −158 |
| **31.9%（平衡点）** | **0** |
| 40% | +690 |
| 50% | +1,538 |
| 100% | +5,775 |

同时，DIRECT 档 912 场（无效率 3.7%）**零复筛成本**，面试官精力不再被无效复筛占用——这正是"把精力集中在最值得深入沟通的候选人身上"的落点。

### 结论稳健性（不是数据巧合）

1. **卡方检验**：复筛池 vs 其余，2×2 列联表 χ²=**346.6**（df=1，p=0.001 临界值 10.83）。
2. **分半验证**：随机 50/50 分割重复 20 次，两半复筛池无效率始终 **49.8% ± 4.1** 与 **50.6% ± 3.9**，对照组 **3.8% ± 0.6** 与 **3.7% ± 0.6**，差异不依赖特定子集。
3. **口径稳健**：44 条 `is_valid` 空值全部按"未判定"剔除、不计入任何分母；复筛池空值率 4.7% vs 其余 3.5%，无显著偏斜，剔除不影响结论。

> 所有数字均由 `interviews.csv` 真实数据算出，**未使用任何补造数据**；75/12 工时为业务方给定口径，非数据推导。交互过程与纠错记录见 [AI_LOG.md](file:///f:/programming/project/gaundeng/AI_LOG.md)。

## 四、建议动作

1. 研发部 / 产品运营部 / 客户成功部：员工内推简历**增加人工复筛前置关卡**（成本 12 工时/次，拦下 31.9% 即回本）。
2. 商业销售部内推流程不动（实测 5.1%，已达标）。
3. 其余 7 个渠道**不加复筛**（1.7%~6.0%，复筛纯属浪费）。
4. **不要用 match_score 阈值去筛**：池内分数不单调，阈值既拦不住高分无效（46.2%），又会误伤。
5. 上线后按 `screened.csv` 的 `screen_action` 追踪拦截率，若连续低于 31.9% 立即回看规则。
